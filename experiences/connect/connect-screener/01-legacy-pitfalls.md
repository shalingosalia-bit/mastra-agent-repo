# Legacy Connect screener: how it works, and the constraints its defects impose

Grounded in `sunspear` on branch `major`: `app/components/connect` and its subdirectories, `app/components/InfoView/InfoViewWidgets/Connect*`, `app/connectors/listings.ts`, and `app/models/connect_listing.ts`; and in `the_wall/essos/lib/http/routes/listing_routes.rb` for what the surface is handed. [`experiences/views/01-legacy-pitfalls.md`](../../views/01-legacy-pitfalls.md) covers sunspear's presentation layer in general, including the variant explosion; this document covers only what is specific to Connect and does not restate it. Measurements belong to [`legacy_assessments/`](../../../reference/legacy_assessments/README.md).

## How the screener exists today

The surface is a dashboard component that owns the whole screen: it resolves or creates a saved filter view, holds the query text, the visible record ids, the page cursors in both directions, separate loading flags for each direction, and an error flag, and it drives every fetch itself through connector modules (`sunspear/app/components/connect/connectListingsDashboard.tsx:52-74, 187-286, 443-448`). Cards are rendered from a tile component whose body is assembled from a table of per-attribute constants (`helpers.tsx:231-261`), each naming a field, its unit, and where applicable its aggregation. A flyout renders the detail view in single and multi variants; a widget carousel renders the AI-derived panels; a separate feed component renders the timeline, fetching the feed and then making further round trips to hydrate the dispositions and users it was given ids for (`ConnectListingStatusFeed/ConnectListingStatusFeedContainer.tsx:42-120`). Dispositions are written through an actions component, and creating a deal from an offering goes through a modal.

## The defect classes

### 1. The screen is one component that fetches, paginates and renders

The dashboard holds bidirectional cursor state, per-direction loading flags, an initialisation flag, and a flag whose comment states its purpose plainly — to prevent infinite re-fetching loops, especially when the API returns empty results (`connectListingsDashboard.tsx:63`). A loop guard as component state is the diagnostic: fetch orchestration lives where rendering lives, so the failure mode of one is a state variable of the other. Nothing in the screen can be rendered from a fixture, because the fixture would have to be a working API. **Constraint:** every component in this stack takes its data as props and performs no fetch. Cursor state, retry, and the distinction between "no results" and "not loaded yet" belong to the container, which stays in the app ([`experiences/design-system/01-component-extraction.md`](../../design-system/01-component-extraction.md)). A component that needs a loop guard has a fetch inside it.

### 2. The displayable attribute set is hardcoded, twice

The card body's field table declares a constant per attribute, carrying the field name, the unit, and for portfolio listings a separate aggregation variant and a default-value twin (`helpers.tsx:231-261`). This is the frontend half of the same defect the service has: a broker attribute nobody has coded is not displayable, so adding one is a change in essos' column list, its filter allow-list, and this table. **Constraint:** what a card shows is driven by field metadata — the field's `display` settings, its unit and dimension, its labels — which [`entity-fields/`](../../../coredata/entity-fields/00-entity-fields.md) already carries on the definition. The component renders a field it has never heard of, and the tenant's configuration decides which fields appear, per [`views/`](../../views/00-views.md).

### 3. The surface is handed ids and display labels, so it fetches again to render

The activity feed returns day groups containing a formatted day label and lists of ids; the feed component then fetches the dispositions by id and the users by id before it can render a row (`ConnectListingStatusFeedContainer.tsx:101-120`). The label it renders is the one the service formatted in a timezone the client passed in, which means the same data renders differently depending on a query parameter and cannot be re-grouped client-side without a round trip. **Constraint:** an operation returns values, and this stack formats them (CN14, CN15). Day grouping, timezone conversion and label text are computed here from timestamps, so a fixture of timestamps is enough to render every state of the timeline, and changing the reader's timezone re-renders without a request.

### 4. One timeline is four components, and its row types are branches rather than renderers

The timeline is a feed component, a list view, a row component and a helper module, with the entry kind decided by a branch and rendered by one of two sibling components (`ConnectListingStatusFeed/`). The client is not carrying legacy's second, superseded feed endpoint — `sunspear/app/connectors/listings.ts:293` calls `/listing_activity_feed` only, and nothing calls `/listing_status_feed`, so that one is dead on the service side alone (`experiences/connect/06-legacy-functionality-map.md`). What the surface does carry is a structure with no extension point: a third entry kind means editing the branch, the list view and the helper. **Constraint:** one timeline component with one row contract, and an entry kind is a member of a closed union with a registered row renderer. An unregistered kind renders as an unknown row rather than disappearing, so a new kind is visible before it is styled.

### 5. The client supplies part of the visibility rule, and the code says so

`Private-Restricted` reaches the client as `Private`, rewritten during serialization (`the_wall/essos/lib/models/listing.rb:108`), so the surface cannot distinguish a restricted offering from an ordinary private one. More consequentially, the client adds a `listing_type = Public` filter for a team without Connect access, and the comment above it states the arrangement precisely: the filter is not redundant with the service's scoping, because the service excludes only `Private-Restricted` and plain `Private` listings pass for every team; the service gates the endpoint on member level and trusts the caller for the public/private split (`sunspear/app/models/connect_listing.ts:156-180`).

Read carefully that is not a hole — the member-level gate is the access boundary, and the comment calls the filter a product control rather than a security one. What it does mean is that the public/private distinction is enforced by whichever caller remembers to ask for it, so a second consumer of the same endpoint — an agent, another client, a direct call — presents a different visible set to the same principal. **Constraint:** every rule that decides what a principal sees is enforced server-side, once, for every caller ([`authz/`](../../../coreservices/authz/00-authorization.md)), and this stack renders the result without contributing to it. A filter this surface adds is a preference the reader chose, never a restriction the system depends on. Where an affordance is unavailable to the reader it renders as unavailable with its reason, rather than absent or mislabelled, which is what makes Sam's guarantee checkable from the UI side (CS8).

### 6. Write affordances are optimistic in appearance but not in contract

Setting a disposition and creating a deal from an offering are separate components, each issuing its own write and reconciling the screen afterwards; the service's idempotency for the second act exists because a screener navigating back and re-confirming produced a duplicate attribution (the reasoning is recorded at length in `the_wall/essos/lib/grpc/implementations/listing_management_impl.rb:50-64`). The surface has no representation of a write in flight that survives a remount. **Constraint:** every write affordance takes a callback and a state (idle, pending, failed with a reason, or settled) supplied as props, so the pending and failed renderings are stories, exercisable without a live API. Whether the underlying act is idempotent belongs to the stack that owns the write (CN13); rendering the four states is this one's.

### 7. A per-source wrapper exists for every shared panel, because the offering has its own schema

The record detail panels are mostly built the right way already: a shared base plus a thin per-context wrapper — `BasePhotosWidget` with `ConnectPhotosWidget`, `BaseEsriWidget` with `ConnectEsriWidget`, `BaseStreetViewWidget` with `ConnectStreetViewWidget` and `LatLngStreetViewWidget`, `ContactsWidget` with `ConnectContactsWidget` over shared card components. The rendering is shared and the wrapper adapts one source's shape to the base's props, which is the presentational/container split arriving by convergence rather than by design. Two things are worth naming. The wrapper exists only because the Connect record's attributes are a different schema from every other record's, so it is work the entity-type decision removes rather than a duplication to consolidate. And one panel has no base at all: `InfoViewWidgets/PropertyLocationWidget/` contains a Connect component and nothing else, so the location panel genuinely exists once, for Connect. **Constraint:** with the offering as an entity type, a panel takes field values and metadata and needs no per-source adapter. A `Base*`/`Connect*` pair is not a defect to unwind so much as a wrapper to delete; a panel that exists only in a Connect form is the one that has to be generalised before it can be shared ([`06-legacy-functionality-map.md`](06-legacy-functionality-map.md) records each one's target).

## What is kept

| Rule | Where it is today | What changes |
|---|---|---|
| A card must say enough to pass or pursue without opening anything | the tile body's field selection and its portfolio aggregations (`helpers.tsx`) | Kept as a default card composition; which fields appear becomes tenant configuration rather than a constant table |
| A portfolio offering aggregates its properties rather than showing the first one | the `SUM` and `MIN_MAX_RANGE` aggregation variants | Kept, as a field-level aggregation the renderer reads from metadata |
| The screener works through a stack of offerings without losing their place, in both directions | the dashboard's bidirectional cursors and its up/down page state | Kept as behaviour, moved to the container; the component receives a page and a position |
| A saved filter view is the unit the screener returns to | the local-view resolve-or-create on mount | Kept, and becomes an instance of [`views/`](../../views/00-views.md) rather than a Connect-specific saved view |
| Passing on an offering asks for a reason | `ConnectPassListingModal.tsx`, and the `reason` column the service stores it in | Kept, and the reason becomes a field value on the disposition write rather than a column on a flags table |
| The detail view distinguishes one offering from several | the single and multi flyout variants | Kept as one component with a selection prop, not two components |
