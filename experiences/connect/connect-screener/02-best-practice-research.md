# Settled answers for a triage surface and a presentational package

**The presentational/container split is settled, and its test is executable.** A presentational component takes plain serialisable props and renders; a container fetches, resolves the tenant, and passes the result down. The useful form of the rule is not the description but the check: if the component renders in a story, a unit test and an agent's composition with no database, the split holds, and if it does not, a container is inside it. [`experiences/design-system/01-component-extraction.md`](../../design-system/01-component-extraction.md) states this for the frontend and [`../../../spec-stack-template.md`](../../../spec-stack-template.md) makes it the definition of the presentational kind.

**A triage queue is a keyboard-first surface, not a table someone clicks through.** The settled shape for working a stack of items — mail clients, code review, moderation queues — is a list with a persistent selection, next and previous that do not require pointing, a decision that can be taken from the list without opening the item, and an undo window on the decision. Legacy's screener has the list and the detail view but no selection model that survives, which is why "navigating back and re-confirming" was a real enough path to cause a duplicate-attribution defect.

**Empty, loading, partial and error are four renderings, and conflating any two is the common defect.** An empty result and an unfetched one look identical in a component that receives only an array, which is how a misconfigured filter reads as an empty mailbox; a partial result — a page loaded, more available — is not the same as a complete one; and an error needs its reason rendered, not a spinner that never resolves. The consequence for the interface is that absence and emptiness must be distinguishable in the props themselves, which is why every collection prop in [`05-interface-and-configuration.md`](05-interface-and-configuration.md) states what absent and what empty each mean.

**An optimistic write needs its state passed in, not inferred.** The settled pattern is a callback plus an explicit state — idle, pending, failed with a reason, settled — because a component that infers pending from a stale prop cannot render the failed case at all, and the failed case is the one that matters. Passing the state in also makes each rendering a story, which is the only way the pending and failed appearances get reviewed before a user finds them.

**Long lists virtualise, and the budget is part of the interface.** Rendering a whole queue is what makes a screener feel slow; windowing is standard and cheap. What is worth stating is that the window size and the row height are props with defaults rather than internal constants, because a rendering budget is a property of rendering — the one legitimate numeric knob in a presentational package.

**Formatting happens at the edge, from an instant, in the reader's locale and timezone.** A service that returns a formatted date has decided the reader's timezone, their locale and their date format on their behalf, and has made re-grouping impossible without a request. The settled arrangement is the reverse: an operation returns an instant, the surface formats it, and changing the reader's timezone re-renders with no round trip. Legacy inverts this and the timeline pays for it (defect class 3 in [`01-legacy-pitfalls.md`](01-legacy-pitfalls.md)).

**Colour, spacing and type come from tokens, so a surface follows the theme rather than restating it.** The token set is authored once and consumed everywhere ([`design-system/`](../../design-system/00-design-system-reference.md)); a component with a literal colour is a component that will be wrong in the next theme, and a component with a literal spacing value is one that will not sit correctly beside its neighbours.

**A queue has specific accessibility obligations, and they are not generic.** Focus must move into a detail view on open and return to the originating row on close; the decision affordances must be reachable and labelled with the offering they act on rather than with the verb alone; arrival of new items in an open list must be announced rather than silently shifting the selection. These are requirements on the components, so they belong here rather than in a general guideline nobody checks.

**What does not apply.**

| Technique a reader would expect | Why it is not paid for here |
|---|---|
| A data-fetching library used inside these components | Fetching is the container's, and a query hook inside a component is the kind declaration in [`00-connect-screener.md`](00-connect-screener.md) being contradicted. The container may use one |
| A client-side store holding domain data | [`livedata/`](../../../coreservices/livedata/00-livedata.md) delivers changed records to an open screen. A second copy of the domain in the client is a cache to invalidate and a source of two truths |
| Infinite scroll owning its own cursor | The cursor is the container's, and the component receives a page plus whether more exists in each direction. Legacy's cursors live in the component, which is defect class 1 |
| A design system, or a component library, of its own | [`ui/`](../../../../packages/shared/ui) ships the components and [`design-system/`](../../design-system/00-design-system-reference.md) the tokens and rules. This stack composes them |
| Static server rendering of the whole surface | The screener is an interactive queue with a live selection; the shell renders server-side like any other route, and that is the app's concern rather than a component's |
| A `Connect*` variant of a shared panel | With the offering as an entity type, its panels are the shared panels configured differently (defect class 7). Variants are what the field system removes the reason for |
| An internationalisation framework decision | Labels come from field metadata and the app's own arrangement. This stack states that formatting is locale-aware and takes the locale as a prop; which library provides it is not a spec-stack decision |
