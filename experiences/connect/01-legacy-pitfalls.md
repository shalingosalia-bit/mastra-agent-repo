# Legacy Connect: how it works, and the constraints its defects impose

Grounded in `the_wall` on branch `major`: `essos/lib/models`, `essos/lib/http`, `essos/lib/grpc`, `essos/lib/filters`, `essos/lib/utils`, `essos/resque`, `essos/db`, and `essos/script`; and in `sunspear/app/components/connect` and `sunspear/app/connectors/listings.ts` for the consumer. Measurements belong to [`legacy_assessments/`](../../reference/legacy_assessments/README.md) and [`reference/modernization/surface-area-reduction.md`](../../reference/modernization/surface-area-reduction.md); this document cites `file:line` and ticket ids only.

## How Connect exists today

Essos is a service inside the_wall's repository with its own MySQL database, its own Resque workers and schedules, and its own OpenSearch index. It exposes two surfaces: a Sinatra HTTP server that sunspear calls for search, listing reads, dispositions, the activity feed and the Outlook setup flow (`essos/lib/http/routes/`), and a gRPC server the monolith calls to read listings, set a disposition, and hand over a forwarded email (`essos/lib/grpc/implementations/listing_management_impl.rb`). Records arrive four ways: a bulk broker feed driven by a GitHub Actions workflow over S3 folders (`essos/script/run_connect_ingestion.rb`, `essos/docs/connect_ingestion_flow.md`), an email a user forwards, which enters through the gRPC `ingest_forwarded_email` handler (`listing_management_impl.rb:149`), a mailbox essos watches through Microsoft Graph subscriptions (`essos/lib/http/routes/internal_outlook_routes.rb`, `essos/resque/ingest_outlook_email_job.rb`), and a crawl of the listing's own URL after a card is created (`essos/resque/listing_url_crawler_job.rb`). Every path converges on one importer (`essos/lib/utils/connect_record_importer.rb`) that writes the listing, its properties, contacts, highlights, images and cross-tenant distributions. Classification and extraction are not essos' — they are HTTP calls to `ai_service` (`essos/lib/connectors/ai_service_connector.rb`). Authentication and authorization are not essos' either: every request costs a gRPC round trip to the monolith to verify a token, and further round trips to read the caller's member level and feature access (`essos/lib/utils/member_level_utils.rb`, `essos/lib/utils/feature_access_utils.rb`).

## The defect classes

### 1. The property grain is a typed column per broker attribute

`listing_properties` carries one column for each attribute any broker has ever sent — physical, financial, lease, sustainability-rating and market attributes side by side — so the table's width is the union of every broker's vocabulary rather than a property of the domain. Unit variants are separate columns rather than one value read in a context (`gla` beside `gla_sqm`; `price_per_sqmeter` on `listings`), which is the arrangement [`coredata/entity-fields/10-multi-currency-fit.md`](../../coredata/entity-fields/10-multi-currency-fit.md) exists to replace. The filterable surface is a hand-maintained allow-list of column names with much of it commented out and a note that the author was unsure whether the fields belonged (`essos/lib/filters/listing_filter_config.rb:3-70`), so exposing an attribute a broker already sends is a code change. **Constraint:** the new design may not give listings a schema of their own. A listing is an entity type and its attributes are field definitions, so a broker attribute arrives as configuration and becomes filterable, derivable and searchable without a migration.

### 2. Visibility is default-open, enforced in the application, and a nil tenant selects the cross-tenant view

A listing is visible to every tenant unless its `listing_type` is `Private-Restricted`, in which case a `listing_distributions` row grants access — expressed as an application scope with a left outer join and a `DISTINCT` (`essos/lib/models/listing.rb:74-82`), not as a database-enforced boundary. The database has no tenant column on `listings` and no row-level security; `team_id` on the child tables is a plain integer with no foreign key, because the tenant it names lives in a different database. Per-tenant children are then filtered in Ruby after every tenant's rows have been loaded, and the filter returns every row when no tenant is supplied: `return records if team_id.nil?` (`essos/lib/models/listing.rb:124-128`).

That branch is not unreachable and it is not an oversight. The tenant-facing routes all pass `serializable_hash(team_id: logged_in_team_id)` (`essos/lib/http/routes/listing_routes.rb:203, 323, 348, 364`), while the admin routes pass `team_id: nil` deliberately, because the support console is meant to see every team's dispositions and grants (`essos/lib/http/routes/admin_listing_routes.rb:44, 88`). So one serializer serves both a tenant-scoped read and a cross-tenant read, and the only thing separating them is whether an argument was supplied.

The service's own position on the wider split is on record in the consumer: the client adds a `listing_type = Public` filter for a team without Connect access, and the comment explains that the filter is not redundant, because the service excludes only `Private-Restricted` and plain `Private` listings pass for every team — the endpoint is gated on member level and trusts the caller for the public/private split (`sunspear/app/models/connect_listing.ts:156-180`). Taken at its word, that is a product control rather than a broken boundary; taken as a design, it means the visible set for one principal depends on which client asked. **Constraint:** a cross-tenant read is a distinct operation with its own authorization and its own audit record, never the tenant-scoped operation with the tenant omitted. Tenancy is resolved by the host and enforced by the database, per [`tenancy.md`](../../tenancy.md) — every read goes through `withTenant()`, cross-tenant visibility is an explicit grant rather than the absence of a restriction, and an absent tenant is an error rather than a wildcard. Filtering another tenant's rows out in application code after loading them is not an implementation detail to improve; it is the mechanism that must not exist.

### 3. The gRPC surface takes the tenant and the actor as arguments

`get_listings` takes a timestamp and returns every listing created after it, with children, to any caller that can reach the port (no tenant filter, no pagination; `essos/lib/grpc/implementations/listing_management_impl.rb:8-11`). `set_listing_status` requires `user_id` and `team_id` in the request body and trusts both (`:35`). The HTTP surface is structured the same way one layer up: for a write the credential is a field inside the JSON body (`__token`, `__admin-auth-token`), and whether the request is an impersonation is a caller-supplied boolean that selects which verifier runs (`essos/lib/http/middleware/auth_middleware.rb:87-98, 128, 137`). Authentication failures are swallowed and printed to stdout (`:112-115, :178-181`), and an unauthenticated request returns `403` (`:65-78`). **Constraint:** no operation may take a tenant or a principal as an input. Both ride the request context, as [`apps/mcp/CLAUDE.md`](../../../apps/mcp/CLAUDE.md) rule 2 already requires of tools and workflows and `apps/mcp/src/wiring.test.ts` asserts. Impersonation is a property of the verified token, never a flag beside it ([`authn/`](../../coreservices/authn/00-authn.md)), and an unauthenticated caller gets the structured-error envelope of [`reference/modernization/23-shared-mechanisms.md`](../../reference/modernization/23-shared-mechanisms.md).

### 4. Run state is inlined on the domain row, and the disposition key is a set of flags

A property carries the state of its own AI enhancement in five columns beside its attributes — status, version, timestamp, error text and a processing-start marker — so a record and the last attempt to enrich it are one row, and a stalled attempt is repaired by a data migration (`essos/db/migrate/20260310000001_reset_ai_status_for_orphaned_listing_properties.rb`). A disposition is a `listing_statuses` row unique on `(team_id, listing_id, status)`, which makes the current disposition a set of flags rather than a state: `PASSED` and `ADDED_TO_PIPELINE` can both be present, one enum member exists to mean "no row at all" (`essos/lib/models/listing_status.rb:20`), and nothing can be withdrawn. `entity_id` records which deal a listing became but is deliberately outside the key, for reasons the code explains at length (`essos/lib/grpc/implementations/listing_management_impl.rb:50-64`). **Constraint:** an attempt and its subject are separate rows. Enrichment attempts are ingest run records ([`ingest/`](../../coredata/ingest/00-ingest.md)) and follow the ledger contract; the current disposition is one live row per `(tenant, listing)` enforced by the partial unique index of [`reference/modernization/23-shared-mechanisms.md`](../../reference/modernization/23-shared-mechanisms.md) §5, with history in the ledger — not a uniqueness constraint that includes the value being made unique.

### 5. Identity is synthesized from a transport header

An extracted listing has no reliable identifier, and the table's unique index is on `(broker_listing_id, broker_company)`, so the importer's input is given one by concatenating whatever the extractor produced with the email's `Message-ID`, falling back to the `Message-ID` alone (`essos/lib/utils/connect_email_ingestor.rb:336-342`). The consequence is stated in the comment: two emails from one broker about different properties would otherwise collide. A `Message-ID` is supplied by the sender's mail client, so record identity is a value the sender controls. **Constraint:** an identifier is minted by Neuro (`id` as UUIDv7, `public_id` as the opaque external form, per [`coredata/entity-fields/04-data-model.md`](../../coredata/entity-fields/04-data-model.md)) and never derived from a transport header. What arrives from outside is recorded as a source reference on the intake run and used for idempotency, which is what `Message-ID` is good for, rather than as the key of the record it produced.

### 6. One reason column holds both a closed vocabulary and truncated exception text

`skip_reason` is documented as the shared vocabulary the jobs write and the sweep's retry policy reads, listed as constants so the two cannot drift (`essos/lib/models/listing_email_ingestion.rb:39-51`). The same column also receives `e.message[0...255]` on three failure paths (`essos/lib/utils/connect_email_ingestor.rb:59, 103, 234`), so a value that the policy switches on may equally be the first 255 bytes of an exception. `ListingUrlIngestion.failure_reason` mixes the same two kinds. **Constraint:** a column a decision reads holds one closed vocabulary. Diagnostic detail belongs in the structured-error envelope on the run record, where it is a field of its own and carries the code the policy switches on separately from the message a person reads.

### 7. Retry, backoff, dead-lettering and idempotency are re-implemented per job

Essos runs no Resque retry plugin, stated in the code as the reason a job takes a single attempt and must stamp a terminal failure itself (`essos/resque/extract_forwarded_email_job.rb:69`). Each path therefore builds its own: a compare-and-swap claim with an attempt counter, a release that refunds the attempt, and a claim-fenced write on the model (`essos/lib/models/listing_email_ingestion.rb:62-98`); an hourly cron that re-drives or abandons rows against a policy of its own with a batch cap, a stranded window derived from another policy's constants, a cool-off and a maximum attempt count (`essos/lib/utils/listing_ingestion_sweep_policy.rb:9-33`); a private backoff array and attempt ceiling in the crawler (`essos/resque/listing_url_crawler_job.rb:15-17`); and a separate retry policy for Graph calls. Every job argument is written to stdout by the shared job hook, which is why a forwarded email has to be stashed encrypted on its row and the job takes an id instead (`essos/lib/models/listing_email_ingestion.rb:106`). **Constraint:** retry, backoff, the attempt ledger, dead-letter triage and idempotency are properties of the bus and the pipeline, not of a workload. They are specified in [`async/`](../../coreservices/async/00-async.md) and [`ingest/`](../../coredata/ingest/00-ingest.md) and consumed; a Connect job that re-implements one is a review finding. A payload is never a job argument.

### 8. The extraction verdict is recomputed instead of carried

The forwarded-email path classifies inside the gRPC handler, hands a listing to a job, and the job classifies the same email again. The code names the consequence: a hosted model is not bit-deterministic at temperature zero, so the second verdict can disagree with the first, and a benign second answer would leave the email owned by neither Connect nor the fallback path — handled by relabelling the row `PROCESSING_FAILED` with a dedicated reason (`essos/resque/extract_forwarded_email_job.rb:44-56`). The split exists because the caller's gRPC deadline cannot fit extraction, and the inline call's timeouts are hand-tuned against the extraction service's own internal cap (`essos/lib/utils/connect_email_ingestor.rb:21-31`). **Constraint:** a classification or extraction result is produced once, recorded on the run, and read by every later stage. Where a deadline forces work into a job, what crosses the boundary is the recorded verdict and a reference to the payload, never an instruction to decide again. Cross-service timeouts are settings, not constants tuned against another service's internals.

### 9. Cross-source matching depends on a lossy key built from tables in code

The same property arriving by broker feed and by forwarded email is matched on a key built by lowercasing the street line, expanding street-type abbreviations, and reducing state and country to their codes against name-to-code maps — all held as constants, with the country map lifted from an earlier migration (`essos/lib/utils/address_normalizer.rb:22-97`). The abbreviation patterns are position-independent, so a leading "St." meaning Saint expands to "street"; matching still succeeds because both sides are normalised identically, which is why the file says the key is lossy by design and built for matching rather than display. Correctness of the whole scheme rests on both paths calling the same builder, stated in the file as a requirement with a named failure mode. The window the match is applied over is a code constant (`essos/lib/utils/connect_record_importer.rb:24`), and when normalisation has produced a wrong stored value the repair is a migration (`essos/db/migrate/20250910200435_fix_jll_street_address_leftover_components.rb`, `20260624201040_backfill_normalized_address_key_on_listing_properties.rb`). **Constraint:** the match key is derived data with a declared derivation, recomputed from the record rather than stored as the only copy, and its inputs — the abbreviation table, the region maps, the window — are tenant-scoped or operator-tunable configuration ([`05-interface-and-configuration.md`](05-interface-and-configuration.md)). The lossy form is never a display value, and a match is a proposal a person or an agent can reject rather than a merge that has already happened.

### 10. The importer accepts every column as input

The importer computes its accepted attribute set from the models themselves — `Model.column_names` minus the primary key and a few guarded columns (`essos/lib/utils/connect_record_importer.rb:46-51`) — so the extraction service's JSON is written to whatever columns it happens to name. The wire shape is the table shape, there is no input contract between the two services, and one file carries dedup, upsert, image delta, contact and highlight replacement, distribution grants, and failure logging to S3 in a single pass. **Constraint:** the boundary between extraction and the record is a declared contract validated before anything is written, which is the map and validate stages of [`ingest/`](../../coredata/ingest/00-ingest.md). Extracted attributes land in `proposed_values` and enter `field_values` only through the normal write path when accepted ([`coredata/entity-fields/04-data-model.md`](../../coredata/entity-fields/04-data-model.md), [`coredata/entity-fields/05-writes-and-calculations.md`](../../coredata/entity-fields/05-writes-and-calculations.md)), so nothing an extractor produces can write a record directly.

### 11. Tunable values live in code, and business rules vary by environment

Thresholds, windows, caps, batch sizes, timeouts and target counts are code constants throughout: the address dedup window, the sweep's batch cap, attempt ceiling, cool-off, stranded window and payload retention, the encrypted payload size cap, the crawler's backoff array, the enhancement job's default and maximum batch size, the preview's batch size, target count and maximum batches, the backfill window, the OAuth state lifetime, and the Graph subscription renewal window. Two exclusion rules are worse than untunable: one fires only in production (`essos/lib/utils/email_exclusion_rules.rb:16`), so non-production ingests mail production would refuse, and one matches `sender.include?('dealpath')` as a substring of the whole address (`:26`). **Constraint:** every threshold, limit, timeout, cap and default is a setting keyed in [`packages/shared/settings`](../../../packages/shared/settings) or tenant-scoped configuration, per [CLAUDE.md](../../../CLAUDE.md) §Code quality principles, and [`05-interface-and-configuration.md`](05-interface-and-configuration.md) is where each one's key, default and degenerate value is stated. A rule may not read the environment class; if it should differ per environment, that is a setting with a different value per environment.

### 12. Reference data and per-tenant corrections ship as schema migrations

Broker logos are inserted by four separate migrations (not seeded; `essos/db/migrate/20250709172000_add_broker_logos.rb`, `20250709172001_add_additional_broker_logos.rb`, `20260407000000_add_new_broker_logos.rb`, `20260811180000_add_connect_broker_logos.rb`), and a listing's brokerage logo is joined on the brokerage's name string (`essos/lib/models/listing.rb:20`). Data corrections go in the same way: normalising imported listings to a preferred format, deleting invalid and incorrect listings, renaming one brokerage, and correcting flags on one brokerage's listings with the ticket id in the file (`20250811140026`, `20250811173154`, `20250929111118`, `20251113102404`, `20260622173553`). The schema of record is meanwhile behind its own migrations: `essos/db/schema.rb:13` predates `sweep_attempt_count` and `payload_marker`, both of which the sweep reads, so loading the checked-in schema produces a database the sweep will not run against. **Constraint:** reference data and defaults are dataset content applied idempotently ([`datasets/`](../../coredata/datasets/00-datasets.md)), and every tenant-facing table or configuration includes a provisioning default so a freshly provisioned tenant is not missing it ([`packages/tenant/core/CLAUDE.md`](../../../packages/tenant/core/CLAUDE.md) rule 10, landing in `packages/tooling/seed` per [`packages/tooling/CLAUDE.md`](../../../packages/tooling/CLAUDE.md) rule 4). Never DDL: that one is this stack's own constraint, against the defect above. A brokerage is a record joined by identifier. Migrations change schema; correcting data is a dataset or a job with a run record.

### 13. Presentation is produced inside the service

The activity feed loads a tenant's dispositions and forwarded-email events with no limit, merges and sorts them in Ruby, groups them by calendar day in a timezone the caller passes, and returns the day's display label already formatted (`'%B %-e, %Y'`) alongside an integer date key derived from `strftime` (`essos/lib/http/routes/listing_routes.rb:508-570`); a second, superseded feed endpoint does the same thing for dispositions alone and is still live (`:461`). Serialization decides display elsewhere too: `Private-Restricted` is rewritten to `Private` on the way out (`essos/lib/models/listing.rb:108`), and timestamps leave in two different epochs: seconds on a listing, milliseconds on a disposition, with a comment explaining that the latter matches what the monolith returns (`essos/lib/models/listing.rb:111-116`, `essos/lib/models/listing_status.rb:31`). **Constraint:** every operation the composition binds returns values. Timestamps leave in one representation; a masked type is a separate authorized field, returned as-is; day grouping, timezone conversion and label formatting belong to [`connect-screener/`](connect-screener/00-connect-screener.md); and a timeline is a paginated query.

## What is kept

Several legacy rules are correct and only their substrate is wrong. Naming them here keeps [`04-proposed-model.md`](04-proposed-model.md) from rebuilding a solved problem, and keeps a reader from mistaking the list above for a verdict on all of it.

| Rule | Where it is today | What changes |
|---|---|---|
| An atomic claim, not a status read, is what stops two workers processing one arrival | `essos/lib/models/listing_email_ingestion.rb:62-76`, and the comment stating why a plain read fails | The mechanism moves to the pipeline's run records; the rule is unchanged |
| A worker that lets go on purpose refunds its attempt; one that dies keeps it | `:80-91` | Becomes the ledger's attempt semantics ([`reference/modernization/23-shared-mechanisms.md`](../../reference/modernization/23-shared-mechanisms.md) §6) |
| A late write must be fenced on the claim it won, or a reclaimed row is overwritten by the loser | `:96-98`, and its use in `essos/resque/extract_forwarded_email_job.rb:28-56` | Unchanged as a rule |
| The point at which an arrival counts as stranded is derived from the source's own retry chain, not set independently of it | `essos/lib/utils/listing_ingestion_sweep_policy.rb:7-11` — "Derived from that chain so the two cannot drift apart" | Kept as a derivation. Only the margin on top of the chain is tunable ([`05-interface-and-configuration.md`](05-interface-and-configuration.md), `strandedMargin`); exposing the total would let an operator set a recovery pass to fight retries still in flight |
| Reconciliation is a pure decision separated from the reads and writes that act on it | `essos/lib/utils/listing_ingestion_sweep_policy.rb` — a pure module with a `Candidate` struct, tested without a database | Kept as written, and as the model for how Connect's own policies are expressed |
| Re-forwarding the same email must not produce a second card | the source-message dedup match over a bounded window, `essos/lib/models/listing_email_ingestion.rb:130-139` | The window becomes a setting; the rule and its fail-safe on a blank key are unchanged |
| A refresh token that rotates on use must be redeemed under a lock | `essos/lib/models/outlook_integration_setting.rb:129-155`, with the vendor behaviour stated in the comment | Kept; the secret itself defers to [`reference/modernization/23-shared-mechanisms.md`](../../reference/modernization/23-shared-mechanisms.md) §1 |
| A webhook's shared secret is compared in constant time | `essos/lib/http/routes/internal_outlook_routes.rb:584` | Kept |
| A paused integration is paused for a stated reason, and the reason decides the recovery path | the three paused states and their recovery notes, `essos/lib/models/outlook_integration_setting.rb:16-27` | Kept as a vocabulary; the states become the acquisition front's health model |
| Excluding Connect's own mail breaks an ingestion loop, and excluding a forwarded broker email does not | `essos/lib/utils/email_exclusion_rules.rb:12-16`, and CON-170, which is the incident where over-broad exclusion dropped real listings | The rule is kept and its inputs become configuration; the environment gate and the substring match do not survive |
| A URL from third-party content is fetched only when its scheme is `http(s)` and every address it resolves to is publicly routable, failing closed on an unresolvable or partly-internal host | `essos/lib/utils/url_safety.rb`, which also states the race it does not close — the host is resolved there and again by the HTTP client — and names the durable fix as an egress proxy | Kept, including the blocked-range list and its handling of IPv4-mapped and NAT64 forms. The stated gap is a requirement rather than an inherited limitation ([`03-requirements-and-user-stories.md`](03-requirements-and-user-stories.md) CN19) |
| A URL is logged as scheme, host and path only, so credentials and signed-URL tokens in the query never reach a log line | `essos/lib/utils/url_safety.rb:74-80` | Kept |
| A crawled page must be shown to describe the same property before its values are merged | the merge gate, `essos/resque/listing_url_crawler_job.rb:92-112` | Kept, and strengthened: the merge becomes a proposal rather than a write |
